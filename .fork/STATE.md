## RELEASE 1.10.2: FAST APP ROUTES (#232) + THE USER GUIDE (2026-11-03, on the owner's word "роби мердж і реліз 1.10.2"; engine only)
Why: an app author measured 0.9-2 s per plugin route and a `JS_FreeRuntime` abort that turned a finished route into a 500 (their report plus a patch against 1.9.7 was reviewed; the patch was ported to 1.10.1 by hand because `script` and `hardTimeoutMs` moved two files). Cause: one sandbox worker for the whole engine, and a `git status` walk of the whole workspace before every app route answered.
What changed: `src/plugins/sandbox.ts` a pool of 2-4 workers (`MOLFAR_VERTEP_SANDBOX_WORKERS`), idle end after 5 min, retire past 192 MB; a per-data-dir read/write gate (calls that may write take the dir alone, GETs share it) because eight parallel read-modify-write handlers lost 6 updates in a test without it; a worker that is still freeing its runtime (`settling`, ended by the worker's `settled` note) gets no call, and calls queued behind one that then fails (`poison`) run again (`notStarted`). `sandbox-worker.mjs` answers from inside the eval callback, before the runtime is freed, and reports `fsWrites`. `runtime.ts` carries `fsWrites` on `PluginRouteResponse` and marks non-GET routes `exclusive`. `src/server/app.ts`: `queueRouteCommit` / `pumpCommits` commit after the answer in batches; files of an app with a route still running (`routesRunning`) or queued wait for that route's commit, not `out-of-band`; `/v1/git/log`, `commit`, `restore` wait for the queue (`whenCommitsSettled`).
Measured (own harness, 1.10.1 vs this, throwaway engine, 8 cores, 3000-file workspace, two runs each, p50): tiny GET 975 -> 17 ms, 4000-item GET 1010 -> 50 ms, POST 1020 -> 21 ms, 4 parallel 3970 -> 200 ms, 8 parallel 7800 -> 170 ms, no failures; counter after 8 parallel POSTs 8/8. A synthetic plugin, not Roleplay: absolute numbers will differ, the ratio should hold.
Known and accepted: routes that arrive during a commit share one commit (30 routes -> 5 commits, label `... (+N more)`), so Undo steps are coarser; a commit still queued when the process is killed is lost as a commit (files stay, the next commit says `out-of-band`); a GET route that writes files is not protected from another GET of the same app (the gate lets GETs share the dir); every successful route, even a read, still queues a commit job and so a background status walk per batch (skipping jobs with no `fsWrites` is the next saving). Store snapshots are taken before a call runs, so two parallel calls can still overwrite each other's store keys: that was true with one worker too.
Checks: typecheck (root; `client-agent` errors are missing deps in a worktree), `plugins.test.ts` 40 pass (3 new: writes of one app never interleave, the data dir is free again after a failed call, an aborting worker never gets the next call), `app-foundation.test.ts` (new: a running route's files are not labelled out-of-band; control run without the fix fails with `out-of-band: apps/twowrite/data/slow.txt`). Targeted groups (plugins, apps, git, sandbox, security, script box): 257 pass, 2 fail on a clean tree too (0600 modes, git inside the sandbox shell: Windows).

## BUILDER NEVER STARTS: NO LIMIT ON THE FRAME (#224, 2026-11-02, branch `claude/close-issues-63-64-outdated-c18073`, engine; not released yet)
Cause found (reproduced in a real browser with a throwaway engine and proxies): `BuilderFrame.build()` awaited `this.ready` with no limit, and the 5-minute build limit starts only after `ready`. When the browser never starts the builder frame (its `frame-ancestors` / `script-src` come from the request's `Host` and `X-Forwarded-Proto`, so a TLS-terminating proxy that does not send `X-Forwarded-Proto: https`, or one that rewrites Host and Origin, blocks it) the shell stayed on "Building the app" for ever: no CPU, no log, no console error in the top window. Reporter on #224 ran it from systemd on a headless Arch box (Firefox and Brave alike, a re-installed app did not help); whether they have a proxy is not known, so this is a probable, not a proven, cause for them.
Fix in `src/builder/browser/host.ts`: the frame page has 30 s to start (the wasm download is not counted: a slow phone, #190), esbuild 120 s after that; each ends in an error that names the likely cause (proxy headers, a frame-blocking extension, what to look for in the console). Second hang found on the way: a proxy that rewrites Host makes the engine's `requestGuard` refuse every POST (403), and the lease loop swallowed it and showed "Another open tab is building this app" for ever; a refused lease request now shows the engine's error (first attempt, or three in a row while waiting). Checked: baseline hangs 150 s without an error, fixed code gives the error card at ~34 s; good proxies (http and https with the forwarded headers) and a direct address build in ~9 s. Not done: the "last good build" wording of the error card when no build ever existed; an engine-side `installing` for ever case (bun install has a 10-minute kill timer; nothing in the tab says how long it has been going) is a second candidate for #224 and is untouched.

## MAX OUTPUT COLLAPSED TO 1 TOKEN ON A FULL WINDOW (2026-11-02, branch `claude/prompt-context-window-debug-239244`, engine only, RELEASED in 1.9.7)
Discord report: with the window set to 64k, long Roleplay chats failed or got ~3 tokens back; unlocked, they worked. Cause: pi-ai's `clampMaxTokens`
(`simple-options.js`) lowers every call's `maxTokens` to `window - its own estimate - 4096` (never below 1). Roleplay already trims the prompt to
`window - reply`, so the library's extra 4096 margin left nothing: the six inspector files the reporter sent give `max_tokens` 1 for 66k, 85k, 95k and
100k (prompt ~98k est.) and 4000 for 110k and unlocked, exactly the ones that worked. OpenRouter's activity list showed no big request for the failed runs
because a 1-token request is rejected or not logged. Fix (`src/models.ts`, `generate`): when the caller names `max_tokens`, the stream call gets a model copy
with `contextWindow: 0`, which switches the library clamp off for that call only. Test: `test/max-output-vs-window.test.ts`. The agent path keeps its own
`clampMaxTokens`. Known and left: Molfar's token estimate is ~25% above the real count for Gemini (99k est. vs 79k real), so a trimmed chat keeps less than
the window allows. Full run: the 26 failures are Windows environment ones (tar, 0600 modes, sandbox, in-browser builder, stdio MCP), none in the model path.
